Problem

왜 만들었나 — 우리 등록 방이 경매에 넘어가도, 알 방법이 없었습니다

방이 경매로 넘어가면 임차인의 보증금과 계약이 위험해집니다 — 그런데 이걸 알려주는 시스템이 없었습니다.

⚠️ 손 놓고 있을 수밖에 없던 이유

  • 전국에 진행 중인 경매만 2만 건 이상 — 우리 방 주소와 사람이 하나하나 비교하는 건 불가능
  • 매일 바뀜 — 새로 나오고, 유찰되고, 낙찰되고, 취하되는 게 하루에도 수천 건
  • 법원 사이트는 검색만 가능 — 우리 주소 목록을 넣어두고 지켜보는 기능이 없음
  • 알게 되는 순간 = 이미 늦은 순간 — 낙찰이 끝난 뒤에 알면 할 수 있는 게 별로 없음

🎯 그래서 목표 4가지

  • 매일 전국 수집법원경매에 나온 집 전체를 시트 하나에 모으기
  • 자동 대조경매 물건 주소 ↔ 삼삼엠투 등록 방, 동·호수까지 비교
  • 변동만 알림일치하는 건에 변화가 생긴 날만 Chat으로
  • 운영 처리 화면운영팀이 확인하고, 조치하고, 기록까지 한 시트에서
한 줄로 — "경매에 넘어간 방에서 계약이 진행되는 일"을 막기 위한 조기 경보입니다.

🏛️ 수집 — 로그인 없이 볼 수 있는 것만

  • 법원경매정보 사이트가 누구에게나 공개한 데이터만 가져옵니다 — 로그인·우회 없음
  • 전국을 지역 묶음으로 나눠 차례로 실행 — 한 번에 다 하면 서버 제한 시간(5분)을 넘김
  • 단계 사이에는 바뀐 것만 전달 — 2만 건을 통째로 넘기면 서버가 버티지 못함

🔨 낙찰 확인

  • 매각결과 페이지를 따로 수집 — 목록에서 사라진 물건 중 실제로 낙찰된 건을 '낙찰 확정'으로 표시
  • 낙찰가·낙찰일까지 기록 — 323건 확정, 같은 작업을 다시 돌려도 중복 없이 안전

📄 시트 관리 원칙 — 중복 없이, 기록은 남기고

원칙내용
한 물건 = 한 줄물건 고유 번호 기준 — 중복 0건
바뀌면 그 줄만 갱신가격·경매일·유찰 횟수가 바뀌면 해당 줄만 고치고 날짜 도장
지우지 않고 표시목록에서 사라져도 줄을 지우지 않고 '사라짐'으로, 낙찰이 확인되면 '낙찰 확정'으로 — 지난 기록이 판단 근거가 됨
필요한 것만 쓰기안 바뀐 줄은 건드리지 않음 — 속도와 호출 한도를 지키는 방법
  • 물건마다 눌러서 바로 보는 상세 조회 링크를 자동으로 답니다 — 법원 사이트엔 물건별 바로가기 주소가 없어서 직접 만들었습니다 (기존 21,785건에도 소급 적용)
  • 칸 설명·범례 탭도 스크립트가 자동 관리 — 시트를 다시 만들어도 안내가 어긋나지 않음

Detail 2 · Matching

구현 상세 ② — "같은 집인가?"를 동·층·호수까지 따집니다

주소 글자가 같다고 같은 집이 아닙니다 — 운영팀 제보를 받아 판정 규칙을 두 번째 버전까지 다듬었습니다.

📐 판정 규칙 — 동(棟)·층 4가지

1경매엔 동이 있는데 방엔 없으면 → 다른 집 ("1동 101호" ↔ "101호")
2경매엔 동이 없고 방엔 있으면 → 같은 집으로 인정 ("203호" ↔ "1동 203호")
3동 이름이 다르면 → 다른 집 ("1동" ↔ "가동")
4층이 다르면 → 다른 집 — 호수에서 짐작되는 층(503호=5층)까지 비교
이 규칙들은 전부 운영팀이 "이거 다른 집인데 같은 집으로 잡혔어요" 하고 알려준 사례에서 나왔습니다 — 규칙은 책상이 아니라 현장에서 나옵니다.

🗂️ 처리현황 탭 — 조치까지 한 화면에서 시트 열기 ↗

  • 일치한 건마다 사건번호 · 주소 · 방번호 · 호스트 · 진행 중 계약 수를 자동으로 채움
  • 일치가 풀리면 이유를 자동으로 구분해서 표시경매가 끝난 건지, 우리 쪽에서 방이 내려간 건지 양쪽을 확인해서 적어줌
  • 운영팀은 처리상태 칸만 기록하면 됨 — 나머지는 매일 자동 갱신
  • 경매 개시일·매각허가 결정일도 법원 데이터에서 자동으로 채워 넣음

🔌 사내 주소검색 API — 주고받는 데이터

보내는 것경매 물건의 지번주소 한 줄 — 정해진 호출 한도 안에서, 일정한 속도로 천천히 요청합니다
받는 것그 주소에 등록된 방 목록 — 방 고유 번호 · 지번/도로명 주소 · 동·호수 상세 · 진행 중인 계약 목록 (호스트 이름·연락처는 응답에 아예 없음 — 대조에 필요한 것만)
넓혀 찾기글자가 딱 같은 주소만이 아니라 부번·건물명이 붙은 등록 주소 후보까지 함께 알려줌
이 API는 개발팀 현희님이 저희 요청 사항(비슷한 주소 후보까지 넓혀 찾아주는 확장 조회 등)에 맞춰 제작해 주셨습니다 — 덕분에 전국 전수 대조가 가능해졌습니다. 감사합니다 🙏

💬 알림 — 조용해야 오래 갑니다

  • 변화가 있는 날만 보냄매일 오는 알림은 아무도 안 봅니다 — 조용한 날이 정상
  • 카드에는 건수 요약만낙찰 단계의 새 일치 건만 상세를 붙이고, 전체 내역은 시트의 변동 기록 탭에
  • 경매 단계만 바뀐 것(진행 중 → 매각)은 새 건으로 다시 세지 않음같은 건이 두 번 알림되지 않도록 기준을 손봤습니다
  • 점검용 수동 실행은 알림이 안 나가는 게 기본점검하다 진짜 알림이 발송되는 사고를 막기 위해 — 실제 발송은 따로 켜야만 동작

⚖️ 수집 원칙 — 법원 판례를 기준으로 선을 그었습니다

  • 데이터 수집(크롤링) 관련 판결들을 먼저 살펴보고, 다음 5가지를 지키도록 설계했습니다
1로그인·인증 우회 없음 — 누구나 볼 수 있는 공개 데이터만
2허용된 만큼만, 천천히 — 요청 사이 간격을 두고, 막히면 쉬었다 재시도
3채무자·소유자 이름이 담긴 항목은 아예 저장하지 않음
4사내 리스크 관리 용도로만 · 외부 공유 금지
5수집 대상은 국가기관의 공개 공고문 — 법적으로 자유롭게 이용할 수 있는 자료
자동화보다 선 긋기가 먼저였습니다 — 회사 이름으로 도는 수집기라면 더욱요.

느낀 점 ① — 이번엔 n8n이 정답이었습니다

앱 리뷰 과제에서는 n8n을 접고 Python으로 갔는데 — 이 과제는 정반대 결론이 났습니다.

🔁 왜 반대 결론이 났나

  • 앱 리뷰는 하루 몇 건, 사람이 승인하는 일 — 제 PC에서 도는 Python이면 충분했습니다
  • 이 과제는 매일 2만 건, 사람이 안 보는 날이 대부분 — 제 노트북이 꺼지면 안 되는 일
  • 그래서 사내 자동화 서버(n8n)에 올렸습니다 — 꺼지지 않고 혼자 도는 게 기준이었습니다
교훈 — 도구에 정답은 없고, 일의 성격이 도구를 고릅니다. 사람 승인이 필요한 일은 내 곁에, 혼자 돌 일은 서버에.

🧗 대신, 서버의 제약에 맞춰 설계했습니다

  • 한 단계당 5분 제한 → 전국을 지역 묶음으로 나눠 차례로
  • 큰 데이터를 넘기면 서버가 버티지 못함 → 바뀐 것만 다음 단계로
  • 사내 API 호출 한도 → 일정한 속도로 천천히, 막히면 쉬었다 재시도
제약을 우회하지 않고 제약에 맞는 구조를 짰더니 — 오히려 안정적으로 돕니다.

느낀 점 ② — 데이터 모으기는 시작일 뿐이었습니다

1
가치는 수집이 아니라 대조와 알림에서 나왔다
2만 줄짜리 시트만 있었다면 아무도 안 열어봤을 겁니다. 등록 방과의 대조, 변화가 있는 날만 오는 알림, 조치를 기록하는 화면까지 이어지고 나서야 쓰이는 도구가 됐습니다.
데이터는 재료고, 결과물은 '사람이 움직일 수 있는 신호'입니다
2
판정 규칙은 현장에서 나왔다
처음엔 "1동 101호"와 "101호"를 같은 집으로 봤습니다. 운영팀의 "이거 다른 집인데요?" 제보가 쌓이면서 동·층까지 따지는 지금의 규칙이 됐고 — 지금도 제보로 다듬는 중입니다.
규칙의 설계 문서는 운영팀의 제보 목록이었습니다
3
알림은 많이 보내는 게 아니라, 필요할 때만 보내는 것
하루 수천 건 변동을 다 알리면 그날로 채널이 조용히 무시당합니다. 동·호수까지 일치한 건의 변화만, 그것도 요약으로 — 조용한 날이 많아야 알림이 신호로 남습니다.
알림의 가치는 보내지 않은 날들이 만듭니다
4
점검하다 사고 난다 — 기본값을 안전하게
점검하려고 돌린 수동 실행이 진짜 알림을 쏘고 기록을 흔드는 일을 겪고 나서, 수동 실행은 알림 없이 도는 게 기본이 되도록 바꿨습니다. 실제 발송은 따로 켜야만 동작합니다.
안전은 '조심하기'가 아니라 '기본값'으로 만드는 것

공유하고 싶은 점 — 바깥 데이터를 지켜보는 일의 공식 6가지

비슷한 과제(외부 데이터를 모아서 비교하고 알리는 일)를 하실 분들께 — 그대로 가져다 쓰세요.

⚖️
선 긋기부터수집 원칙 문서화
수집을 시작하기 전에 로그인 우회 없음 · 천천히 · 개인정보 미저장 · 사내 한정을 문서로 — 회사 이름으로 도는 자동화의 기본입니다.
🧩
쪼개고, 바뀐 것만시간·용량 제한 대응
큰 작업은 묶음으로 나누고, 단계 사이엔 바뀐 것만 넘기세요 — 자동화 도구의 제한 안에서 큰 데이터를 다루는 공식입니다.
🔕
변한 것만 알리기요약 카드 + 기록 탭
알림에는 건수 요약만, 상세 내역은 시트에 — 채널이 무시당하지 않아야 알림이 삽니다.
🧪
점검 실행은 조용하게기본값 안전
점검·복구용 수동 실행이 진짜 알림을 못 보내게 기본값으로 — 실제 발송은 따로 켜야만.
🔁
다시 돌려도 안전하게과거 데이터 채우기
과거 데이터를 채우는 스크립트는 몇 번을 돌려도 결과가 같게 만들어 저장소에 남기세요 — 다음 복구가 반나절에서 5분이 됩니다.
📝
시트 설명도 코드로범례·메모 자동화
칸 설명·범례 탭을 스크립트가 관리하게 — 시트를 다시 만들어도 안내가 어긋나지 않습니다.

막혔던 곳 7군데 — 같은 길을 가실 분들을 위한 지도

외부 사이트 × 사내 API × Chat 알림 — 서로 다른 시스템이 만나는 지점에서 문제가 났습니다.

#문제원인해결
1전국 수집이 도중에 끊김서버가 한 단계에 5분까지만 허용전국을 지역 묶음으로 나눠 차례로 실행
2단계 사이에서 서버가 멈춤2만 건을 통째로 다음 단계에 전달바뀐 것만 골라서 전달
3사내 주소 API가 접속을 차단보안 장비가 이름 없는 프로그램을 차단프로그램 이름표를 달고, 일정한 속도로 천천히 호출
4낙찰 안 된 물건이 '낙찰'로 잘못 표시상태 코드의 뜻을 짐작으로 사용공식 코드표를 구해서 판정을 바로잡음 — 짐작 말고 원본 확인
5Chat 카드에 경고 문구가 뜸웹훅 봇은 버튼을 처리하지 못함버튼 대신 글자 링크로 교체
6물건 상세를 링크로 보낼 수 없음법원 사이트에 물건별 바로가기 주소가 없음눌러서 볼 수 있는 내부 조회 페이지를 직접 제작
7같은 건이 두 번씩 알림됨경매 단계가 바뀐 걸 새 건으로 인식'같은 건' 판단 기준에서 단계를 제외
이번에도 — 문제는 계산 로직이 아니라 서로 다른 시스템이 만나는 지점에서 났습니다.

🚀 기능 — 경보에서 대응 체계로

  • 판정 정확도 계속 높이기잘못 잡은 것·놓친 것 사례를 모아 규칙을 다음 버전으로
  • 대응 요령 만들기처리상태 기록이 쌓이면 상황별 대응 매뉴얼과 통계로 발전
  • 급한 건 더 크게 알리기진행 중인 계약이 있는 일치 건은 더 강하게 표시
  • 수집 범위 다시 보기지금은 건물만 — 빠져 있는 유형(토지 등)이 필요한지 점검

항목현재개선
남의 사이트 의존법원 사이트가 개편되면 멈출 수 있음구조 변화를 감지하면 바로 알리게 강화
물량 증가물건 수가 크게 늘면 시간 제한에 다시 걸림일정 수준을 넘으면 묶음을 더 잘게 나누기
서버 한 곳 의존자동화 서버 장애 = 수집 공백PC에서 돌릴 수 있는 예비 스크립트 정기 점검
가장 큰 위험 — 남의 사이트 위에 지은 집이라는 점. 법원 사이트가 바뀌면 멈춥니다. 그래서 처음부터 다시 지을 수 있는 스크립트를 늘 준비해 둡니다.

Wrap-up

한 문장 정리 — 그리고 부탁 3가지

💬 이번 과제가 남긴 한 문장

"자동화의 진짜 결과물은 데이터가 아니라,
사람이 움직일 수 있는 신호였다."
  • 일을 하는 건 2만 줄의 시트가 아니라 변화가 있는 날의 알림 한 장이었고
  • 판정 규칙은 운영팀의 제보가 완성했고
  • 안전은 조심하기가 아니라 기본값(알림 없는 점검 모드 · 기록 보존)이 지켰습니다

🙏 부탁 3가지

  • 알림이 오면 처리상태 칸에 결과를 남겨주세요기록이 쌓여야 대응 매뉴얼과 규칙 개선으로 이어집니다 · 처리현황 열기 ↗
  • "이거 다른 집인데?" 싶으면 바로 알려주세요지금의 판정 규칙도 전부 그런 제보에서 나왔습니다
  • 이렇게 지켜보면 좋을 다른 바깥 데이터가 있으면 말씀 주세요수집 → 대조 → 변동 알림 구조는 그대로 다시 쓸 수 있습니다
