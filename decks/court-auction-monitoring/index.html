● 법원경매 모니터링 — 왜 만들었나
Problem

왜 만들었나 — 우리 등록 방이 경매에 넘어가도, 알 방법이 없었습니다

방이 경매로 넘어가면 임차인의 보증금과 계약이 위험해집니다 — 그런데 이걸 알려주는 시스템이 없었습니다.

⚠️ 손 놓고 있을 수밖에 없던 이유

  • 전국 진행물건 2만 건+ — 등록 방 주소와 사람이 일일이 대조하는 건 불가능
  • 매일 바뀜 — 신규 개시·유찰·낙찰·취하가 하루에도 수천 건씩 변동
  • 법원 사이트는 검색 전용 — 우리 주소 목록을 넣어 모니터링하는 기능이 없음
  • 알게 되는 시점 = 이미 늦은 시점 — 낙찰 확정 후에 알면 대응 여지가 좁아짐

🎯 그래서 목표 4가지

  • 매일 전국 수집법원경매 진행물건 전체를 시트 마스터 DB로
  • 자동 대조경매 물건 주소 ↔ 삼삼엠투 등록 방, 동·호수까지
  • 변동만 알림일치 건에 변화가 있는 날만 Chat 카드
  • 운영 처리 화면운영팀이 확인·조치·기록까지 한 시트에서
한 줄로 — "경매 개시된 방에서 계약이 진행되는 일"을 막기 위한 조기 경보입니다.

🌅 운영팀의 하루 — 이렇게 돌아갑니다

  • 아침 — 경매 DB 백업이 먼저 돌고, 이어서 등록 방 대조가 실행됨
  • 변동 없는 날 — 아무 알림도 오지 않음 (조용한 날 = 정상)

Detail 1 · Collect & Store

구현 상세 ① — 전국 2만 건을 매일, 시트 하나에 쌓습니다

🏛️ 수집 — 비로그인 공개 API만

  • 법원경매정보의 공개 API를 순수 HTTP로 재현 — 로그인·브라우저 우회 없음
  • 전국을 지역 그룹으로 분할 실행 — n8n 노드당 300초 제한에 맞춤
  • 노드 간에는 변경분(delta)만 전달 — 2만 행을 통째로 넘기면 메모리 초과

🔨 매각결과 보강

  • 매각결과검색을 별도 크롤 — 리스트에서 사라진 물건 중 낙찰 확정 건을 SOLD로 마킹
  • 낙찰가·낙찰일·허가결정기일까지 기록 — 323건 확정 보강, 재실행해도 안전(멱등)

📄 마스터 DB 규칙 — 중복 없음 + 이력 보존

규칙내용
1행 = 1물건법원 물건 고유 ID 기준 — 중복 0
변경은 갱신가격·기일·유찰이 바뀌면 해당 행만 갱신 + 날짜 스탬프
삭제 대신 마킹리스트에서 사라져도 지우지 않고 GONE, 낙찰 확정은 SOLD — 이력이 곧 판단 근거
쓰기 최소화변동 없는 행은 건드리지 않음 — API 한도·속도 확보
  • 물건마다 내부 상세 뷰어 링크 자동 생성 — 법원 사이트가 딥링크를 지원하지 않아 직접 만들었습니다 (21,785행 백필)
  • 헤더 메모·범례 탭도 스크립트가 관리 — 수동 서식이 어긋날 일이 없음

Detail 2 · Matching

구현 상세 ② — "같은 집인가?"를 동·층·호수까지 따집니다

주소 문자열이 같다고 같은 집이 아닙니다 — 운영팀 피드백으로 판정 규칙을 v2까지 다듬었습니다.

📐 판정 규칙 v2 — 동(棟)·층 4규칙

1경매엔 동이 있는데 방엔 없으면 → 불일치 ("1동 101호" ↔ "101호")
2경매엔 동이 없고 방엔 있으면 → 일치 허용 ("203호" ↔ "1동 203호")
3동 이름이 다르면 → 불일치 ("1동" ↔ "가동")
4층이 다르면 → 불일치 — 호수에서 유추한 층까지 대조
이 4개 규칙은 전부 운영팀이 실제 오탐 사례를 제보해서 생겼습니다 — 규칙은 책상이 아니라 현장에서 나옵니다.

🗂️ 운영_처리현황 — 조치까지 한 화면에서

  • 일치 건마다 사건번호 · 주소 · 방번호 · 호스트 · 활성 계약 수 자동 채움
  • 일치가 풀리면 해제 사유를 자동 분류경매가 끝난 건지, 방이 삭제된 건지 교차 확인해서 표기
  • 운영팀은 처리상태 컬럼만 기록 — 나머지는 매일 자동 갱신
  • 개시결정일·매각결정기일도 법원 사건 상세에서 자동 보강
내부 주소 API는 레이트리밋에 맞춰 정속 호출 — 서비스에 부담을 주지 않는 속도로 매일 전수 대조합니다.

Detail 3 · Alert & Safety

구현 상세 ③ — 변동만 알리고, 법적 경계 안에서 돕니다

💬 알림 — 조용해야 오래 갑니다

  • 변동이 있는 날만 발송매일 오면 아무도 안 봅니다 — 조용한 날이 정상
  • 카드는 요약형 — 그룹·사유별 건수만확정 단계(매각·허가·납부) 신규 건만 상세 줄, 상세 내역은 변동로그 탭
  • 경매 단계가 바뀐 것(진행중→매각)은 신규·해제로 중복 보고하지 않음변동 키에서 단계를 분리한 설계
  • 수동 실행은 기본 테스트 모드 — 알림·상태 미변경유지보수하다 실알림이 나가는 사고 차단, 복구용만 라이브 옵션

⚖️ 수집 정책 — 판례 기준으로 설계

  • 크롤링 형사·민사 판례(여기어때 사건 등)를 기준으로 경계를 먼저 그었습니다
1인증 우회 없음 — 비로그인 공개 API만
2허용 상한 준수 + 요청 간 딜레이 + 거부 시 백오프 (우회 금지)
3채무자·소유자 성명 필드는 저장하지 않음 (개인정보 최소수집)
4내부 리스크 관리 용도 한정 · 외부 재배포 금지
5대상은 국가기관의 법정 공고 (저작권 비보호 저작물)
자동화보다 경계 설정이 먼저였습니다 — 회사 이름으로 도는 크롤러라면 더욱.

Part 1 · Lessons

느낀 점 ① — 이번엔 n8n이 정답이었습니다

앱 리뷰 과제에서는 n8n을 접고 Python으로 갔는데 — 이 과제는 정반대 결론이 났습니다.

🔁 왜 반대 결론이 났나

  • 앱 리뷰는 하루 몇 건, 사람이 승인하는 일 — 내 PC의 Python이면 충분
  • 이 과제는 매일 2만 건, 사람이 안 보는 날이 대부분 — 내 노트북이 꺼지면 안 되는 일
  • 그래서 사내 n8n 서버에 올렸습니다 — 상시 무인 실행이 도구 선택의 기준
교훈 — 도구에 정답은 없고, 과제의 성격이 도구를 고릅니다. 승인이 필요한 일은 내 곁에, 무인으로 돌 일은 서버에.

🧗 대신, 제약을 설계로 받아들였습니다

  • 노드당 300초 제한 → 전국을 지역 그룹으로 분할
  • 대용량 전달 시 메모리 초과 → 변경분(delta)만 노드 간 전달
  • 내부 API 레이트리밋 → 정속 호출 + 거부 시 백오프
제약을 우회하는 대신 제약에 맞는 구조를 짰더니 — 오히려 안정적으로 돕니다.

느낀 점 ② — 데이터 수집은 시작일 뿐이었습니다

1
가치는 수집이 아니라 대조와 알림에서 나왔다
2만 행 시트만 있었다면 아무도 안 열어봤을 겁니다. 등록 방과의 대조, 변동이 있는 날만 오는 알림, 조치 기록 화면까지 이어지고 나서야 쓰이는 도구가 됐습니다.
데이터는 재료고, 제품은 '운영팀이 움직일 수 있는 화면'입니다
2
판정 규칙은 현장에서 나왔다
처음 규칙으로는 "1동 101호"와 "101호"를 같은 집으로 봤습니다. 운영팀의 오탐 제보가 쌓여 동·층 규칙 v2가 됐고 — 지금도 피드백으로 다듬는 중입니다.
규칙의 스펙 문서는 운영팀 제보 목록이었습니다
3
알림은 총량이 아니라 신호여야 한다
하루 수천 건 변동을 다 알리면 그날로 채널이 음소거됩니다. 동호수 일치 건의 변동만, 그것도 요약으로 — 조용한 날이 많아야 알림이 신호로 남습니다.
알림의 가치는 보내지 않은 날들이 만듭니다
4
수동 실행이 사고를 낸다 — 기본값을 안전하게
점검하려고 돌린 수동 실행이 실알림을 쏘고 기준선을 흔드는 걸 겪고, 수동 실행 = 테스트 모드를 기본값으로 바꿨습니다. 라이브는 명시적으로 켜야만 동작합니다.
안전은 주의가 아니라 기본값으로 만드는 것

Part 2 · Trouble Map

트러블슈팅 7건 — 같은 길을 가실 분들을 위한 지도

외부 사이트 크롤 × 사내 API × Chat 알림의 경계면에서 만난 문제들입니다.

#이슈원인해결
1전국 크롤이 한 노드에서 실패n8n 노드당 300초 실행 제한지역 그룹으로 분할 실행
2노드 간 데이터 전달 시 메모리 초과2만 행을 통째로 체인에 전달각 노드가 변경분(delta)만 반환
3사내 주소 API 403 차단WAF가 기본 Python UA 차단식별 가능한 UA 지정 + 정속 호출
4낙찰 아닌 물건이 SOLD로 오염상태코드 의미를 추정으로 사용공식 코드표 확보 후 판정 교정 — 추정 말고 원전 확인
5Chat 카드에 경고 문구 노출웹훅 봇은 버튼 위젯 처리 불가버튼 대신 인라인 텍스트 링크
6물건 상세를 링크로 못 보냄법원 사이트가 딥링크 미지원(SPA)내부 상세 뷰어를 직접 만들어 링크 제공
7같은 건이 신규+해제로 이중 보고경매 단계 전이가 변동으로 잡힘변동 키에서 단계(그룹)를 분리
이번에도 — 문제는 로직이 아니라 경계면(외부 사이트·사내 API·알림 채널)에서 났습니다.

보완하고 싶은 점 — 판정 정밀도와 운영 루프

🚀 기능 — 경보에서 대응 체계로

  • 판정 정밀도 계속 보정운영팀 처리현황 피드백으로 오탐·미탐 사례 수집 → 규칙 v3
  • 운영 처리 루프 정착처리상태 기록이 쌓이면 대응 매뉴얼·통계로 발전
  • 대응 우선순위활성 계약이 있는 일치 건은 더 강하게 알리기
  • 수집 범위 검토현재 건물류만 — 제외 유형(토지 등)의 필요 여부 재점검

항목현재개선
비공식 크롤 의존법원 사이트 개편 시 중단 위험구조 변경 감지 + 실패 알림 강화
규모 성장그룹당 처리량이 늘면 타임아웃 재발물량 임계 도달 시 그룹 재분할
n8n 단일 의존워크플로 장애 = 수집 공백로컬 스크립트 백업 경로 정기 점검

Wrap-up

한 문장 정리 — 그리고 부탁 3가지

💬 이번 과제가 남긴 한 문장

"자동화의 진짜 산출물은 데이터가 아니라,
사람이 움직일 수 있는 신호였다."
  • 2만 행의 시트가 아니라 변동이 있는 날의 알림 한 장이 일을 하고
  • 판정 규칙은 운영팀의 제보가 완성했고
  • 안전은 주의가 아니라 기본값(테스트 모드·이력 보존)이 지켰습니다

🙏 부탁 3가지

  • 알림이 오면 처리상태 컬럼에 결과를 남겨주세요기록이 쌓여야 대응 매뉴얼과 규칙 개선으로 이어집니다
  • "이건 같은 집이 아닌데?" 싶은 오탐을 제보해주세요판정 규칙 v2도 전부 제보에서 나왔습니다
  • 대조하면 좋을 다른 외부 데이터가 있다면 말씀 주세요수집→대조→변동 알림 구조는 그대로 재사용할 수 있습니다
